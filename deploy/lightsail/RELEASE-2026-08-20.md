# Release runbook — 20 Aug 2026

For this specific release: **58 changed files and 2 migrations**, going out the week
of a customer demo.

> `deploy.sh` in this directory is Docker-based (`BACKEND_IMAGE`, `docker-compose`).
> The live Lightsail box is **not** Docker — it runs nginx + php8.4-fpm directly
> out of `/var/www/carevance/backend`, with the frontend built on the box. This
> runbook describes the server as it actually is. Reconcile or delete `deploy.sh`
> afterwards; a deploy script that doesn't match production is a trap for whoever
> reaches for it at 2am.

**Deploy backend first, then frontend, then the desktop installer — verifying after
each.** Not because the order is delicate, but because when something breaks you
want to know *which step* broke it. Two of the three outages on 20 Aug were deploy
process failures, not code failures.

---

## 0. Pre-flight (2 minutes, do not skip)

```bash
cd /var/www/carevance/backend

# Extensions. A missing one makes composer refuse the WHOLE install, which then
# ships code against a stale vendor/ that fails at BOOT, not at the feature.
for e in ctype curl dom fileinfo gd iconv intl mbstring pdo_pgsql simplexml tokenizer xml xmlreader xmlwriter zip; do php -m | grep -qix "$e" || echo "MISSING: $e"; done

# A backup you can roll back to. Takes seconds; the alternative is a bad afternoon.
pg_dump --format=custom --file=/tmp/pre-release-$(date -u +%Y%m%dT%H%M%SZ).dump \
  --host=127.0.0.1 --username="$(sed -n 's/^DB_USERNAME=//p' .env | head -1)" \
  "$(sed -n 's/^DB_DATABASE=//p' .env | head -1)"

# Where you are now, so rollback is a known commit rather than a guess.
git rev-parse HEAD | tee /tmp/rollback-sha
```

**Stop if any extension is missing.** Install it before going further.

## 1. Backend

```bash
cd /var/www/carevance/backend
git pull

# Stale compiled manifests reference packages that may no longer exist. This is
# what produced "Class Barryvdh\DomPDF\ServiceProvider not found" on 20 Aug.
rm -f bootstrap/cache/packages.php bootstrap/cache/services.php bootstrap/cache/config.php

composer install --no-dev --optimize-autoloader
```

### The migrations

Two, both **additive** — new columns and new tables, no drops, no rewrites:

| Migration | Does |
|---|---|
| `add_identity_and_hierarchy_to_tasks` | Adds `organization_id`, `created_by`, `parent_id`, `type`, `resolution`, `number` to `tasks`; backfills tenant from project and numbers per tenant |
| `create_leave_types_and_ledger` | Creates `leave_types` + `leave_ledger`; backfills leave types from `organizations.settings` |

```bash
php artisan migrate --force
```

**The task migration is mandatory.** The deployed code selects columns that do not
exist until it runs — every task query 500s in the gap. Keep that gap short.

**The leave migration is inert.** It creates tables nothing reads yet; the balance
your product shows still comes from the JSON quota. Deploying it now costs nothing
and means the schema is in place when accrual is wired up after the demo.

```bash
php artisan config:clear
php artisan config:cache
sudo systemctl restart php8.4-fpm nginx
```

> `config:clear` before `config:cache`. Caching re-runs `bootstrap/app.php`, so if
> the app cannot boot, `config:cache` is the command that fails — which is exactly
> how the 20 Aug outage presented, and why it looked like a caching problem rather
> than a missing package.

### Verify before moving on

```bash
# 401, not 500. 401 means it booted and routed; 500 means it did not.
curl -s -o /dev/null -w "%{http_code}\n" https://carevancetracker.duckdns.org/api/auth/me

# The scheduler must run clean — it drives timers:close-idle every minute.
php artisan schedule:run

# Silent is good.
tail -5 storage/logs/laravel.log
```

Then **log in through the browser.** The 401 above proves the app boots; only a real
login proves auth works.

## 2. Frontend

```bash
cd /var/www/carevance/frontend
npm ci
npm run build
sudo systemctl reload nginx
```

`npm ci`, not `npm install` — install can silently resolve a different tree than the
lockfile, which is not what you tested.

### Verify

Hard-reload the app (Ctrl+Shift+R) and check three things that are new in this
release and visible in seconds:

1. **A task shows a key** like `CV-14` in the list — proves the task migration ran
   *and* the frontend is the new build.
2. **The event log pages at 15 rows** with the header staying put as you scroll.
3. **A manager account cannot see the Payroll section**, but still sees My Payroll.

If keys are missing but the page looks new, the migration did not run.

## 3. Desktop — `CareVance-Tracker-1.2.3-x64.exe`

Install on the tracked machines. This is the build where URL capture actually works:
the PowerShell helper was sealed inside `app.asar` where an external process cannot
read it, so **every packaged build before 1.2.3 silently captured no URLs at all**.

### Verify

On one machine, browse a site for two minutes, then check the timeline:

- The row is named for the **site**, not "Google Chrome"
- Its duration is **minutes, not 1s**

Old rows stay as they are — the fix cannot repair history.

## Rollback

Backend, if the app will not boot:

```bash
cd /var/www/carevance/backend
git reset --hard "$(cat /tmp/rollback-sha)"
rm -f bootstrap/cache/*.php
composer install --no-dev --optimize-autoloader
php artisan config:clear && php artisan config:cache
sudo systemctl restart php8.4-fpm nginx
```

**Do not roll the migrations back.** Both are additive: the old code ignores the new
columns and tables entirely, so reverting code alone is sufficient and safe.
`migrate:rollback` on the task migration would **drop `number` and `created_by`**,
losing the per-tenant keys and reporters — data the forward migration cannot
reconstruct. Rolling code back is reversible; rolling that data back is not.

Database, only if data is actually wrong:

```bash
pg_restore --clean --if-exists --dbname="$DB_DATABASE" /tmp/pre-release-<stamp>.dump
```

## Still outstanding after this release

- **Backups are not running.** `backup-to-s3.sh` is written and unrun. Until one
  restore has been done and timed, this deployment has no stated RPO or RTO.
- **`SENTRY_LARAVEL_DSN` is unset**, so error tracking is installed and inert. Set
  it and the next break arrives as a notification rather than a customer message.
- **Leave accrual is dormant** — tables deployed, nothing reads them. Wiring it up
  needs a backfill for existing employees, which is the step that would otherwise
  drop every balance to zero. Do it after the demo, not before.
