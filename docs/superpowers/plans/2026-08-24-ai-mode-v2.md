> **⚠ PARTLY SUPERSEDED — read `docs/superpowers/specs/2026-08-24-ai-mode-query-graph-design.md` first.**
>
> The v3 query-graph design replaces this plan's grammar with a pipeline of
> pre-aggregated steps, because v2's one-entity-per-plan rule cannot express a
> cross-entity question ("who is on leave with productivity above X, compared with
> today's present employees").
>
> - **Still valid as written:** Task 13 (derivation), Task 16 (retrieval + prompt),
>   Task 18 (frontend types), Task 19 (golden plans).
> - **Do NOT build as written:** Tasks 14 and 15. Build the validator and executor
>   against the v3 grammar instead — building them for v2 first is throwaway work.
> - **Wrong in this plan and in the v2 spec:** "two entities → refuse". Under v3 that
>   is a two-step pipeline that must work.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **A dead agent returns `null`, not a failure.** The v2 foundations were built by a
> workflow that lost two agents mid-phase; each one had written its test and died
> before writing the implementation, and the run continued because `null` is not an
> error. After every task, the check is `ls` the file AND run the test — a green

The v1 plan embedded every line of every implementation. This one does not, and the
reason is not brevity: Tasks 13 and 15 have to be discovered against a live 221-table
schema, and a pre-written body for those would be invention presented as instruction.
What IS pre-written is the part that cannot be discovered — the interfaces, the
assertions, and the traps. Where a body is genuinely determined (Task 17), it is given.

## Global Constraints

All of the v1 plan's Global Constraints still apply in full. These are the additions
v2 introduces:

- **The model never authors an aggregation.** Expanding the vocabulary is not the same
  as letting it write SQL. Every plan still executes through Eloquent so
  `BelongsToOrganization`'s global scope applies structurally.
- **Never `SELECT *`.** Row mode selects from `list_columns` only.
- **The exclusion list is global, structural and by pattern** (§10) — applied at
  derivation, at every role, to dimensions, list columns and filters alike. A refusal
  NAMES the column: "PAN is not available through this tool."
- **Retrieval runs before planning, always.** The prompt carries the top 5 entities,
  never the catalogue. This is what holds planning near the measured ~3s as coverage
  grows; a prompt that grows with the schema makes latency degrade as the product
  improves.
- **A derived metric must declare `origin: 'derived'` and say so in `notes[]`.** A
  naive `AVG(net_pay)` returning ₹76,313 where the truth is ₹91,575 is the exact
  failure this project already hit. Honesty at read time is what converts it into an
  override instead of a shipped wrong number.
- **`payroll_items.month_year` is a `YYYY-MM` string.** Dimensions declare
  `date_format`, and the executor compares in the column's own format. A `Y-m-d` bound
  against a `Y-m` column matches nothing — silently.
- **An unresolvable period is a refusal, never a guess.** A wrong range answers a
  different question than the one asked, confidently.
- **Zero and negative both mean "use the default"** — for `limit` and for retrieval's
  `top`. This bug has been fixed twice already; do not reintroduce it a third time.
- **Every refusal names the thing it refused.** "I can't answer that" with no subject
  gives the reader nothing to rephrase against.

## Decisions this plan makes

Three things the spec leaves open, decided here so seven tasks do not each decide them
differently:

### D1 — Concept keys are the public vocabulary; derived table keys fill the rest

`SchemaIntrospector::derive()` keys by table (`payroll_items`); `MetricOverrides` keys
by concept (`payroll`). **No alias map exists yet, and this mismatch is the single
highest-risk item in the plan** — 22 golden plans, the whole v1 test suite and every
§8 worked example are written in concept keys.

So `SemanticLayer::entities()` returns **both**, with concepts winning:

- the seven concept keys (`payroll`, `attendance`, `leave`, `employees`, `assets`,
  `work`, `hiring`) stay exactly as they are, now built as `derive()[table]` with
  `MetricOverrides::forEntity(concept)` merged over the top;
- every other org-scoped table appears under its own table-name key;
- a table already claimed by a concept does **not** also appear under its table name —
  one entity, one key, or the retriever offers the planner the same table twice and the
  prompt pays for it.

`EntityRetriever` already handles both spellings (its synonym targets list
`payroll` and `payroll_items`), so this needs no retrieval change.

### D2 — The validator resolves periods; the executor never sees a token

`PlanValidator` calls `PeriodResolver::resolve()` and returns the filter with the
concrete `{start, end}` attached **and the original token retained** for the note. Two
reasons: an unresolvable token has to be refused before any query is built, and the
executor stays a pure function of a resolved plan, which is what makes it testable
without freezing time.

### D3 — `notes[]` is assembled by the executor, from three sources

Metric notes (curated caveats), the resolved period in words ("1 Jul 2026 – 31 Jul
2026"), and derived-metric honesty (§12, including the count of zero/null inputs). One
assembly point, because a note added at the controller cannot see what the query did.

### Task 13: SemanticLayer becomes derived, curated and cached

**Files:**
- Modify: `backend/app/Services/Ai/SemanticLayer.php`
- Modify: `backend/tests/Unit/Ai/SemanticLayerTest.php`
- Test: `backend/tests/Unit/Ai/SemanticLayerDerivationTest.php` (new)

**Interfaces:**
- Consumes: `SchemaIntrospector::derive()`, `MetricOverrides::forEntity()`
- Produces (existing, unchanged signatures):
  - `entities(): array` — now concept keys + derived table keys, per D1
  - `entity(string $key): ?array`
  - `metric(string $entity, string $metric): ?array`
  - `dimension(string $entity, string $dimension): ?array`
- Produces (new):
  - `listColumn(string $entity, string $column): ?array`
  - `cached(): array` — the derived layer, memoised
  - `promptCatalogueFor(array $entityKeys): string` — the retrieved subset only
  - `promptCatalogue(): string` — **keep**, now `promptCatalogueFor(all)`.
    `QueryPlannerTest` asserts the prompt contains `avg_net_pay` and carries no row
    data, so deleting this breaks that test rather than the prompt quietly emptying

**The three rules that decide whether this task is correct:**

1. **An override beats derivation, and the merge is per key, not per entity.** A
   curated `avg_net_pay` must not delete the fifty derived metrics beside it on the
   same table.
2. **Every entity whose row belongs to a person exposes an `employee` dimension** (§4),
   synthesised from the `user_id` foreign key. Grouping by employee is what turns "how
   many" into "who", and "who" is most of what an admin asks.
3. **Caching is schema-level, not tenant-level.** The derived layer contains no tenant
   data — table and column names only. Key it on a schema fingerprint so a migration
   rebuilds it; never on `organization_id`, which would multiply one identical
   catalogue by the tenant count.

### Task 14: PlanValidator v2

**Files:**
- Modify: `backend/app/Services/Ai/PlanValidator.php`

**Interfaces:**
- Consumes: `SemanticLayer`, `PeriodResolver::resolve()`, `SchemaIntrospector::isExcludedColumn()`
- Produces: `validate(array $plan): array` — the normalised v2 plan, or throws
  `UnsupportedQuestionException`

Normalised output shape (what the executor may assume, so it needs no defensive code):

```php
[
  'entity'   => string,
  'mode'     => 'aggregate'|'list',
  'metrics'  => list<string>,   // [] in list mode
  'columns'  => list<string>,   // [] in aggregate mode
  'group_by' => list<string>,   // [] in list mode
  'filters'  => list<array{field: string, op: string, value: mixed, period?: array{token: string, start: string, end: string}}>,
  'having'   => list<array{metric: string, op: string, value: mixed}>,
  'sort'     => ?array{by: string, dir: 'asc'|'desc'},
  'limit'    => int,
]
```

**All eight §5 rules, each with a refusal that names the thing.** Plus:

- **`contains` escapes `%` and `_`.** An unescaped `%` returns the whole table — the
  same bug `SearchController` already guards against. Escaping belongs here, not in the
  executor, so it cannot be forgotten by a second caller.
- **An excluded column gets its own refusal**, distinct from "unknown field": the data
  exists and we will not expose it, which is a different sentence from "there is no
  such column" and the difference matters to whoever is reading it.
- **`limit`: `> 0 ? min(500, n) : 20`.**

## Not in this plan — needs a decision

Two requirements that are on record and that **neither the v1 plan nor the v2 spec
covers**. Both are listed here rather than silently omitted, because the current code
does neither and a reader of this plan would reasonably assume otherwise:

1. **AI mode is one assistant, and a refusal should fall back to prose.** Today
   `SearchAskController` returns a bare 422 and the user gets "I can't answer that
   from your HR data." For a question that is conversational rather than analytical
   ("what does F&F mean?"), the right answer is prose from the chat path — never a
   made-up number, but not a dead end either. This needs its own task; it touches the
   controller's refusal branch and the command bar's error state.
2. **Write actions — propose / preview / confirm.** Read-only is the whole of v2.
   Anything that mutates needs the three-step shape through real endpoints, and
   payroll stays read-and-prepare only: never a state transition.

Neither is a v2 blocker. Both should be scoped before v2 ships, so the gap is a
decision rather than a discovery.
