01Phase 0 — safety

D0Two things that ship before anything else

Both surfaced while verifying the claims in this document. Both are losing money or leaving a closed run editable today, both are cheaper than the observer work below, and neither depends on any other decision here landing first.

Ship first
Eight professional-tax jurisdictions that do not levy PT

PTStateService::STATE_CONFIGS deducts professional tax in eight places where none exists in law: Chhattisgarh :155, Goa :163, Himachal Pradesh :170, Jammu & Kashmir :179, Uttarakhand :240, Chandigarh :259, Dadra & Nagar Haveli :273, Daman & Diu :281.

Money leaving real employees' pay on every run. The fix is per-state data, not architecture — it does not wait for the statutory_slabs migration.

Ship first
Two guards that are already dead

in_array($run->status, ['paid','released']) at EnhancedPayrollController:479 and PayrollDepartmentController:1593. Nothing in the system ever writes status 'paid', so both guards are no-ops for approved and disbursed.

Consequence: quickSaveCtc and approveArrear both succeed against a disbursed run right now. Replace both literals with PayrollMonthlyRun::CLOSED_STATUSES, which already exists at PayrollMonthlyRun:45. Two lines.

Verified against code Chandigarh's top band is ['min' => 25001, 'max' => null, 'amount' => 250] — ₹250 flat every month, ₹3,000 a year, ₹500 over the Article 276(2) constitutional cap. That is the one revision 1 named. It is also the least of it: the other seven charge a tax that does not exist. Nothing in calculate() distinguishes a researched slab from an invented one, and CLAUDE.md's standing rule already says it — "several states levy none. Never default a missing state to a real one."

Two smaller defects in the same file: getAnnualLimit() (:515-540) folds Maharashtra's February special of ₹300 into maxMonthly and multiplies by 12, returning ₹3,600 against a real collection of ₹2,500 — so the cap check is itself broken. And Arunachal Pradesh is absent entirely, which fails safe to ₹0 but should be explicit.
D1How to make a closed run actually immutable

Roughly twenty-five ad-hoc status guards exist today, two of them dead (above). Seven distinct code paths write money onto payroll_items across ten statements. The eighth path someone adds next quarter will have no guard at all.

Option A
Model observer

PayrollItem::saving throws when the parent run is closed, unless a governed-override context is bound in the container.

+ catches every Eloquent write, present and future · + one file · − blind to query-builder mass operations

Option B
Database trigger / CHECK

Postgres trigger refusing UPDATE on payroll_items when the parent run status is closed.

+ absolute, survives raw SQL · − tests run on SQLite and the app on Postgres, so it must be written twice and can drift — and CLAUDE.md already flags schema drift as a live hazard

Option C
Service-layer gateway

Every money write routes through one PayrollItemWriter that owns the status check.

+ cleanest architecture · − requires editing seven call sites and protects you from none of the eighth; a new controller can still reach the model directly

✓ Chosen — A, in three parts
Observer + mass-delete guard + enumerate-and-assert

1. The saving observer. 2. A deleting guard plus removal of the relation mass-delete at PayrollAutoProcessService:137. 3. A test that reflects over every controller method writing a money column and asserts each throws on a closed run.

Part 3 is what makes it durable: a new endpoint fails CI until someone deliberately handles the closed case.

Correction to revision 1 Revision 1 listed "PHP-level only, raw SQL bypasses it" as a live caveat and implied the observer would miss the COALESCE increments in PayrollAutoProcessService (:270, :309, :336, :393). That is wrong. Those are $item->update([...]) on a model instance — the DB::raw() is the value, not the query mechanism — so Eloquent events fire normally and the observer catches all of them. Option A is stronger than revision 1 claimed, not weaker.
Verified against code — what the observer genuinely cannot see One true bypass. PayrollAutoProcessService:137 is $run->items()->delete() — a HasMany mass delete, which fires no model events at all. An observer guarding saving will not see it, and neither will one guarding deleting. It is currently fenced by an ad-hoc in_array($run->status, ['draft','processing']) at :136, which is correct today and invisible to the enumerate-and-assert test. This is the hole to close, and it matters beyond D1: it is a hard delete on a model with no SoftDeletes, so it destroys exactly the history D2's differences report and D4's versioning depend on.

One constraint on D4 and D6. Four of those writes — :270, :309, :336, :393, all incrementing custom_earnings — pass an Illuminate\Database\Query\Expression as the attribute value. The observer fires, but it cannot read the resulting number, and the in-memory model afterwards holds an Expression rather than a decimal. A guard that only asks "is the parent run closed?" works fine. A version-writer that wants to record old → new — which is precisely what D4's supersede and D6's computed_value need — gets nothing usable from those four sites. Convert them to read-modify-write before building the version table, or accept four blind spots in the audit trail. (The fifth increment, overtime_pay at :371, computes its value in PHP and is readable — it needs no change.)

Guard count. Thirteen in_array guards on run status gate a write, not nine; a further twelve use ===/!==, so the real ad-hoc surface is about twenty-five. There is no DB enum backing any of it — the migration column is string('status', 30)->default('draft') with a stale comment that still lists paid and omits approved, released and disbursed.

Write paths. Six sites across ten statements, plus a seventh the earlier count missed: PayrollFilingController:2126 writes variable_pay with no run-status guard of any kind.

Confirmed absent. No app/Observers/ directory, zero ::observe( calls, zero CREATE TRIGGER, no booted() hook on PayrollItem.
Keka's approach: they don't block writes — they make a finalized month structurally unreachable, and require an explicit Rollback (typed CONFIRM + a reason) to reopen it. Same outcome by a different route. Option A reproduces it at a fraction of the cost.
Why not B or C

The DB trigger is genuinely stronger, and I'd take it if our test and production databases matched — they don't, and a guard that exists in production but not in tests is a guard you will eventually break without noticing. The service gateway is the cleanest architecture and the weakest protection: it secures the seven paths that exist and none of the eighth.

02Phase 1 — detective controls

D2How to build the four comparison reports

Payroll Differences, Negative Cost, Duplicate, Reconciliation. These are what make greytHR accurate in practice — the payroll officer sees the anomaly before payday rather than after the EPFO rejection.

Option A
Four independent endpoints

Write each report as its own controller method and query.

+ fastest to first report · − four query shapes to maintain, and the diff logic gets copy-pasted three times

Option B
SQL views + generic runner

Define each as a database view, expose through one generic report endpoint.

+ least PHP · − views can't take runtime parameters cleanly (which two months?), and we have no existing report infrastructure to hang them on

✓ Chosen — C
One diff primitive, four presentations

A single PayrollComparisonService that returns component-level deltas between two runs. Payroll Differences is its three presentations (item-wise / employee-wise / consolidated); Negative Cost and Duplicate are filters over one run; Reconciliation is a headcount assertion.

One place where "what changed" is defined — which is also what the override register and the payslip explainer will need later.

Verified against code — check the baseline survives before promising the ranking The sequencing argument below depends on there being three months of history to diff. Confirm there is. PayrollAutoProcessService:137 hard-deletes every item on the run when a rebuild happens, and PayrollItem has no SoftDeletes, so any month that was reprocessed has lost its prior state. Run a count against the real tenant before committing to "this report ranks the backlog" — if the baseline is already gone for the months that matter, D2 still earns its place, but as a forward-looking control rather than a diagnostic one.
Keka's approach: none of this. Keka ships a payroll-components comparison report, but report customisation is its single most-cited complaint on G2. greytHR's Payroll Differences (three modes) and Negative Cost Report have no Keka equivalent. This is a place to beat both.
Why this is Phase 1 and not Phase 6

Run Payroll Differences over the real tenant's last three months before fixing anything. It converts the rest of the remediation from a flat list into a ranked one — you'll see which of the twenty money defects are actually costing rupees in our data, and in what order. Cheapest group on the roadmap, highest information yield.

03Phase 2 — one engine, and what happens when inputs move

D3How to collapse four tax engines into one

Engine A (payroll run) is correct. B (payslip) is a flat 5%. C (the /compare and /what-if endpoints) is on FY 2024-25 slabs with no 87A. D is an orphan that double-counts cess.

Option A
Extract a shared library

Pull the maths into a new package and refactor all four callers onto it.

− keeps four call sites alive, and therefore four future opportunities to diverge again

Option B
Rewrite clean, migrate all

New engine built to spec, migrate every caller, delete all four.

− a rewrite of the highest-risk code in the system, and engine A already encodes two non-obvious correct behaviours you would have to rediscover

✓ Chosen — C
Delete D, repoint B and C at A

Engine A's 87A is assessed on taxable income (not gross) with marginal relief, and its surcharge bands are contiguous. Both are subtle, both are right, and the code carries comments explaining the bug each one fixed. Keep it; retire the rest.

Only D is a true deletion. B and C are live and must be repointed under test.

Verified against code Engine A is as described. PayrollCalculatorService:945 assesses 87A on max(0, $annualIncome - STANDARD_DEDUCTION_NEW) with marginal relief at :958-963; surcharge bands at :63-68 are contiguous half-open with their own marginal relief at :599-607. Old-regime 87A has no marginal relief, which is correct — none exists in law.

Engine B is the flat 5% — Payroll/SalaryCalculationService:331-335, reached from PayslipController:33.

Engine C is not a service. It is inline in PayrollFilingController (calculateOldRegimeTax:1536, calculateNewRegimeTax:1551) serving the live /compare and /what-if routes. FY 2024-25 slabs confirmed at :1554-1565; no 87A anywhere in either method. Its PF is min($annualCtc × 0.40 / 12, 1800) (:1291, :1375, :1479) — revision 1 wrote this as min(basic, 1800), which understates how synthetic the basic is.

Engine D is genuinely orphaned. TaxSimulatorService has zero references outside its own declaration — no route, no DI, no test. It takes a total_tax that already includes cess and re-applies 4% at :45-46. The identical bug was already fixed in EnhancedPayrollController:860-864; the orphan copy was left behind.

Scope correction. Revision 1's line "deletion is the only refactor that cannot introduce an arithmetic bug" does not survive this: only D is deleted. B and C are live paths whose outputs will change when they move to A — which is the point, but it needs regression tests against known payslips before the switch, not after.
What this one change fixes

SalaryCalculationService keeps its payslip-assembly job — only the statutory block moves. Removing it fixes six defects at once: the flat-5% TDS, the FY24-25 slabs, PF-as-a-fraction-of-CTC, the double cess, the ESI ceiling test that ignores the contribution period, and the basic / 208 overtime divisor (:325-326).

On ESI specifically: a period-aware service already exists — Payroll/EsiContributionPeriodService::isCovered — and is already used by the run path (PayrollAutoProcessService:576) and one controller. The two period-blind tests are PayrollCalculatorService:279 and SalaryCalculationService:155. This is a repointing job, not new logic.

D4What happens when an input changes after processing

Today a correction overwrites the payroll item in place, and there is no record that the earlier figure ever existed. This is the decision that everything in the position document rests on.

Option A
Keka's model — freeze and roll back

Finalize freezes the month. Correcting it requires an explicit, irreversible Rollback that clears payslips and bank statements, then re-finalize.

+ proven, simple, cheap · − destructive; Keka's own docs say "cannot be undone" and that documents are "cleared and regenerated"

Option B
Always recompute on read

The item is a view over current inputs.

− a payslip stops being a statement of fact on a date

✓ Chosen — C
Versioned supersede

A correction writes a new immutable version of the payroll item; the old one is retained and marked superseded, with a reason and an actor. Payslips bind to a version, not to the item.

+ correct and auditable · − a payroll_item_versions table and a current_version_id; moderate work

Correction to revision 1 — the mechanism, not the conclusion Revision 1 said "payslips re-render live at download, so reprocessing silently changes a PDF that was already emailed." The conclusion holds; the mechanism is wrong, and the difference changes what D4 has to build.

Money is read from stored columns, not recomputed: PayrollPdfService:115-121 reads $item->basic, gross_salary, total_deductions, net_pay directly. PayrollDayBasisResolver::forStoredItem (:102-113) deliberately prefers the frozen salary_divisor_days, with a comment saying a locked or disbursed item must never re-derive against live config. Someone already thought about this. The payslip changes because the item is overwritten in place — which is still exactly D4's problem, by a different route.
Verified against code — three things D4 must decide that revision 1 didn't know about 1. There are two payslip paths with different semantics. PayrollController:501/:536 renders fresh through Dompdf on every request; PayslipController::downloadPdf:268-293 serves a pre-generated file from payslips/{user_id}/{period_month}.pdf. D4 binds payslips to a version — it must say which path wins, or versioning ships while a stale file is still served off disk.

2. Identity fields genuinely do read live. PayrollPdfService:92-103 pulls employee and org identity — bank account, PAN, UAN, designation, org logo — at render time. Change a bank account today and an already-issued payslip restates. The version snapshot needs to cover identity, not just money.

3. The attendance guard already half exists. Payroll/PayrollPeriodGuard is built and wired into two paths — AttendanceTimeEditRequestController:240-248 and PayrollAutoProcessController:262-267, both returning 422. The hole is one file: LeaveRequestController:327 (approve) and :697 (approveRevoke) call through to applyApprovedLeaveToAttendance(), which saves and deletes AttendanceRecord rows for arbitrary back-dated ranges with no run check — the exact scenario PayrollPeriodGuard's own docblock names and never got hooked into. Nothing recomputes the money afterwards. LockedPayrollPeriodGuardTest covers only the time-edit path.

Confirmed absent: no payroll_item_versions, no superseded column, no SoftDeletes. The only versioning artefact is engine_version, a scalar stamp whose own migration docblock states the policy — "Nothing is recomputed — the policy is fix-forward". It records which engine wrote the current row; it does not retain the prior one.
Keka's approach: option A, and it is harsher than it first sounds. Rollback pulls in everything changed since finalization — "salary revisions made after payroll finalization will take effect and may generate arrears" — so a rollback intended to fix one LOP day can silently restate the whole month. They compensate with input cut-off dates (attendance and IT-declaration), making late inputs structurally impossible rather than merely detectable. Copy the cut-off dates. Don't copy the destructive rollback.
Why diverge here of all places

We already store template_snapshot on every item — PayrollItem:91, cast to array at :167 — so we are halfway to versioning without having planned it. A later migration even names it as the precedent for freezing. And this is the decision that makes the strategic claim true: "every figure traceable back to the work that earned it, and every hand that touched it" is only true if a superseded figure still exists to be traced.

Sequencing that de-risks it: ship freeze-plus-explicit-reopen semantics first (Keka parity, days of work) but build it on the version table from the start. You get the parity behaviour immediately and the audit trail without a rewrite.

Prerequisite from D1: convert the four COALESCE increments to read-modify-write before the version writer exists, or those four paths write versions with an unreadable old value.

D5Locking granularity

A 200-person run always has three exceptions. The question is whether those three block the other 197.

Option A
Two-state: open / closed

One boolean per run.

− all-or-nothing; the three exceptions hold everyone

Option B
Keka's — one lock + maker-checker

Lock the month, gated by an approval workflow.

− their own docs show per-employee rollback as the workaround, which tells you the single lock isn't enough in practice

✓ Chosen — C
greytHR's four tiers + Keka's cut-offs

Inputs lock (attendance, LOP, claims — with a configurable auto-cutoff date) → month lock → per-employee lock → payslip publish, decoupled from lock.

Lock 197, keep working on 3, publish payslips only for the clean set.

Verified against code — one tier is cheaper than budgeted, one gap is unbudgeted Cheaper: the inputs-lock tier is mostly built. PayrollPeriodGuard exists and works; it needs hooking into two more call sites in LeaveRequestController (see D4). Budget call sites, not a subsystem.

Unbudgeted: nothing decides what happens to run-level aggregates when 3 of 200 employees are unlocked. recomputePayrollRunTotals (EnhancedPayrollController:556-573) sums every item on the run and rewrites the run header. Under per-employee locking it will happily restate the totals of a locked month while three items are being edited. It has to become tier-aware, or the month lock means nothing at the aggregate level.
The hybrid is the point. greytHR has the better tier model; Keka has the better input discipline. An auto-cutoff date on attendance means a late regularisation cannot silently invalidate a verified figure — it is the elegant half of Keka's design, and it is independent of their rollback model.

04Phase 3 — overrides

D6How an override is stored and applied

Override capability already exists, ungoverned — through annual_ctc, custom_deductions[] and the arrear endpoints. The question is what shape to give it, not whether to have it.

Option A
Keka's — fallback resolution

The override is a standing per-employee property that shadows the structure value. "If no override is set, Keka uses the value from the employee's salary structure."

+ elegant, survives reprocess by construction · − cannot express "this month only", carries no per-occurrence reason, and gives you nothing to report on per run

Option B
Adjustment lines

The override is a delta line added to the item, like a journal entry.

+ naturally auditable · − you lose "what would it have been", which is exactly what makes a differences report explainable

✓ Chosen — C
Applied layer, both values kept

Override rows evaluated at compute time and snapshotted onto the item, storing both value (what was applied) and computed_value (what the engine would have produced).

The pair is what makes the override register meaningful, the differences report self-explaining, and a reversal trivially computable.

Verified against code — all three ungoverned paths confirmed, and worse than described (a) annual_ctc. PayrollDepartmentController::updateEmployeeTemplate:833-908 validates and writes it with no run-status guard, no reason field and no audit write — only 'updated_by' => auth()->id(). quickSaveCtc:1568-1615 is guarded only by the dead ['paid','released'] check.

A live bug inside that path. processEmployeePayroll writes $template->update(['annual_ctc' => $request->annual_ctc]) at :1015, and only then checks for a disbursed run at :1025. A request that is rejected has already mutated the employee's CTC. Fix this alongside the D0 guard work — it is two lines of reordering.

(b) custom_deductions[]. Accepted per-request at :995-998, summed at :1249-1256, persisted at :1479. No cap, no approver, no reason, no audit record.

(c) Arrears. createArrear:334-346 has 'reason' => 'nullable|string' — optional — and the original_*/revised_* figures are caller-supplied and validated against no salary record. approveArrear:452-550 writes no audit log and works on an approved or disbursed run. Notably rejectArrear is the only one of the three that requires a reason: today it is easier to grant money than to refuse it.

The permission flag has nothing to hang on. Copying Keka's per-component "allow this component to be overridden" flag assumes an authorization layer. CLAUDE.md is explicit: 0 policies, and authorization is inline in controllers. Either budget a policy layer as part of D6, or state plainly that the flag is enforced inline like everything else — but don't cost it as free.
Keka's approach: option A for components, entered as an annual figure in a grid at Payroll Admin → Operations, gated by a per-component flag "Allow this component to be customized and overridden at the employee level." Overrides are not live on entry — "Perform Process Payroll to update the override information in the system." Copy the permission flag and the apply-on-process timing. Diverge on storage.
D7How long an override lives

This looks like a detail and is not. It determines whether a payroll officer can predict what next month will do.

Option A
Copy Keka exactly

Three different lifetimes: components permanent, PT/ESI/LWF/TDS date-ranged, PF a boolean that carries forward until switched off.

− "If you don't want this overridden PF amount to be reflected in the next month, you have to select No." Three lifetimes for one concept is a support-ticket generator.

Option B
Run-scoped only

An override applies to exactly one run and must be re-entered each month.

+ safest, nothing carries forward by surprise · − makes a recurring override (a court-ordered garnishment, a long-running TDS instruction) unusable

✓ Chosen — C
One model: date-ranged, open-ended permitted

effective_from + nullable effective_to. Every Keka behaviour becomes a special case: permanent = open-ended; PF-until-cancelled = open-ended, then closed; range-bound = as-is.

One rule to explain, one to test, one to display in the register. Show the end date on the override row so nothing is a surprise.

The argument, on its own terms

Three lifetimes for one concept means a payroll officer cannot answer "will this still be here next month?" without knowing which kind of override they are looking at. That is the whole case, and it stands without appeal to a second reader having reached the same view — revision 1 offered that as corroboration, which it isn't: a second reader of the same documentation, framed the same way, is agreement rather than evidence.

D8What absorbs the delta when a component is overridden

Our structure is entirely residual — Special Allowance is whatever remains after Basic, HRA and Conveyance come out of CTC. So "set Basic to ₹6,00,000" has two possible arithmetic meanings and the engine cannot guess.

Option A
Always CTC-preserving

The residual absorbs every delta; gross never moves.

− cannot express a genuine correction to an understated component

Option B
Always CTC-additive

Overriding a component raises gross.

− silently breaks the employee's stated CTC, which is the number in their offer letter

✓ Chosen — C
Explicit mode, residual as a role, reject on negative
balance_mode      'preserve_ctc' (default) | 'increase_gross'
balancing_target  component that absorbs; default = the designated residual

Make "residual" a role with an ordered fallback chain of taxable components behind it — not a hardcoded Special Allowance. If a CTC-preserving override would drive the residual negative, reject it with an error naming the maximum permitted value.

Keka's approach — worth copying precisely. Special Allowance is their universal sink: it absorbs LOP pro-rating ("Adjust the difference amount against Special Allowance"), PF proration, unclaimed reimbursements and lapsed FBP. Critically, their PF article states the fallback: "If there is no Special Allowance component, the PF proration adjustment will be applied to the next available taxable component." That single sentence proves it is a role with a fallback chain, not a named component. Copy that design.

What Keka does not document — and we must decide: what happens when the residual would go negative. No article addresses clamping, cascading or allowing a negative. That silence is why their support knowledge base carries articles about unexplained payslip figures.
Also worth stealing: the LOP threshold

Keka's LOP flag is three-state, not two — exempt / exempt up to N LOP days then applies / fully applied, via a Set Threshold control. That is a genuinely good piece of design and it is cheap to copy when we build the per-component flags.

Note the house rule this interacts with: CLAUDE.md says net pay is stored signed and a negative must not be clamped to zero, because payroll validation is what should stop the run. "Reject on negative residual" is a validation refusal at override-entry time, which is consistent — it stops the override, not the number.

05Phase 4 — income tax

D9How monthly TDS is computed

Today the annual projection is this month's gross times twelve, and the month's TDS is a twelfth of the resulting tax — so a month with LOP annualises the reduced gross and under-deducts, no true-up ever happens, and a mid-year revision never corrects earlier months.

Option A
Keep projected ÷ 12

Recompute the projection each month.

− the current defect; there is no reading under which this is correct

Option B
Full-FY restatement each month

Recompute the whole year and restate prior months' TDS.

+ arithmetically purest · − restating a finalized month is precisely what we must never do, and it would contradict D4

✓ Chosen — C
Cumulative YTD true-up over remaining months
annual_tax  = tax(YTD paid + this month + projected remaining + prev employer)
remaining   = annual_tax − TDS already deducted − prev employer TDS
this_month  = remaining ÷ months left in FY

Corrections flow forward and absorb into the months that remain. Finalized months stay immutable.

Verified against code The defect is real and sits in PayrollAutoProcessService: $annualProjected = $payableGross * 12; at :593, then $tds = round(($taxCalc['total_tax'] ?? 0) / 12, 2); at :607. Revision 1 quoted the second line as a bare $totalTax / 12 — the defect is identical, but quote it accurately in any document an auditor might read. Note also that :598 subtracts the FBP exclusion from the annualised base before slabbing, so the replacement must preserve that step.

PayrollCalculatorService:543 carries the same ÷ 12 shape in calculateMonthlyTDS and needs the same treatment.
Keka's approach — this is option C, and their refinements are worth taking too. Their IT computation page exposes exactly the three fields a true-up needs: Net Income Tax Payable / Tax paid till now / Remaining tax to be paid. The bonus setting says it outright — "Select No to distribute TDS over the remaining months". Three details to copy:
  • April is the base month — "no change logs are shown for April, as it is the base month for the financial year's tax projections."
  • Declared until February, approved thereafter — projections run on declared amounts, switching to approved once proofs are reviewed. Warn the employee, as Keka does.
  • Previous-employer income is entered per month, not as an annual lump — which is what lets it fold into the same YTD ledger.

06Phase 5 — statutory data

D10Where PT, LWF and tax slabs live, and who may edit them

36 PT jurisdictions and 15 LWF states live as PHP constants with no effective dates. Recomputing March uses today's slab. Eight of the PT jurisdictions levy no professional tax at all — see Phase 0, which does not wait for this decision.

Option A
Constants + effective dates

Keep them in PHP, add a date dimension.

− a slab correction becomes a deploy; no history query; no audit of what changed when

Option B
greytHR's — tenant-editable grid

Admins edit Salary From / Till / Amount / Deduction Month per state.

− a tenant editing a statutory slab is a compliance liability wearing a feature's clothes

✓ Chosen — C
greytHR's schema, Keka's permissions
statutory_slabs
  kind, state_code, jurisdiction_code, gender, effective_from, effective_to
  frequency, deduction_months json, slabs json
  employer_amount, annual_cap, source_note

Vendor-maintained, shipped as migrations, read-only to tenants. Tenants pick a jurisdiction; we own the rates. Per-employee override is the escape hatch.

07Phase 6 — effective dating

D11A revision effective mid-month
Option A
New rate for the whole month

− overpays; and it is what we do today, since effective_from is ignored entirely

Option B
Old rate, arrear next month

+ simple · − the payslip for the month is knowingly wrong, and the employee sees it

✓ Chosen — C
Segmented split-rate

Split the pay period at the revision date and rate each segment separately. CompensationTimeline::segmentsForMonth() already implements this correctly and has zero production callers. This is a wiring job.

Verified against code segmentsForMonth() is at Payroll/CompensationTimeline:69; its only callers are four assertions in CompensationTimelineTest. The class docblock says so itself — "this resolves the timeline and splits a month into rate segments. It does NOT yet feed the payroll engines."

Every live engine reads the mutable scalar and divides by twelve with no date awareness: PayrollAutoProcessService:438,463, Payroll/SalaryCalculationService:41,70, ProcessPayrollRunEmployees:133,148. None of the three references SalaryRevisionLetter, effective_from, or CompensationTimeline.

The paths that do read effective_from are all after-the-fact and all whole-month: PayrollFilingController:2011-2027 computes arrears as (new_ctc − old_ctc)/12 × monthsElapsed using diffInMonths, so a mid-month effective date is truncated to whole months and the partial month is silently dropped.
Keka's approach — option C, with one mechanical detail worth copying exactly. Their worked example, for a 20th-to-19th cycle with a revision effective 1 April: 
Mar 20–31 = (30,000 × 12) / 31 = ₹11,612.9
Apr 1–19  = (35,000 × 19) / 31 = ₹21,451.6
                              total = ₹33,064.5
Both segments are divided by the pay-period day count — not by each segment's own calendar month. That shared denominator is what makes the segments sum to exactly one month's pay. Get it wrong and every mid-month revision is off by a few hundred rupees in a way nobody can explain.
One place to diverge

Keka refuses negative arrears — "Employee's previous salary must be lower than the current salary for arrears to be calculated." So a back-dated downward revision silently produces nothing. Don't copy that. Allow a negative arrear and route it through override approval, where a human sees it. A recovery that silently doesn't happen is still a wrong payslip.

08Phase 7 — Labour Codes

D13Implementing the 50% wage rule

In force since 21 Nov 2025. Wages must be at least 50% of total remuneration; the excess in allowances is reclassified into wages. PF, gratuity, bonus and leave encashment all key off that definition. Central and state implementing rules are still landing, so orgs will adopt on different dates.

Option A
Compute at runtime from components

Derive the wage base whenever payroll runs.

− recomputing a pre-adoption month would apply today's rule to it, which is wrong and unprovable to an auditor

Option B
Restructure templates at adoption

One-time migration raising Basic to 50% across the board.

− destroys the original structure; you can never recompute a pre-adoption month, and the employee's offer letter no longer matches their template

✓ Chosen — C
Stored parallel wage base, date-gated
// on payroll_items — what was actually used, that month
statutory_wage_base   decimal(14,2)
wage_base_rule        'pre_code' | 'code_on_wages_50pct'

// on organizations
code_on_wages_effective_from  date nullable

The structure stays as agreed with the employee; the statutory base is computed, stored per month, and gated on the org's adoption date. An EPFO audit asks exactly this question: what base did you use, and why.

Correction to revision 1 — the gratuity claim was overstated Revision 1 said the fixed-term gratuity change is "one year, not five — so GRATUITY_MIN_YEARS = 5 is now wrong as a constant." The one-year rule applies to fixed-term employees; the five-year qualifying period still stands for regular employees. The constant at PayrollCalculatorService:36 (used at :312) is not wrong — it is unconditioned. It needs an employment-type dimension, not a new value.

Tie this to the house rule already in CLAUDE.md: gratuity must route through calculateGratuityForSettlement(), which applies the five-year floor and the statutory ceiling, while the raw calculateGratuityOnExit() applies neither. The employment-type condition belongs in the settlement path, so both callers inherit it.
Neither Keka nor greytHR handles this without vendor engineering — third-party analysis of both is explicit that wage-definition reconfiguration for the labour codes requires an implementation ticket. This is the one area on the whole roadmap where we can be ahead rather than catching up.

09What this adds up to

Of thirteen decisions, four copy Keka closely, four deliberately diverge, three are hybrids taking greytHR's structure with Keka's discipline, one is territory neither occupies, and one has no competitor dimension at all.

The two questions neither vendor answers, which we now own:
1. Slab effective-dating — when you recompute a past month, whose slab applies? Decided in D10: the period's own.
2. A negative residual — when a CTC-preserving override or LOP pro-rating would drive Special Allowance below zero. Decided in D8: reject with the maximum named, never clamp silently.

The consequence inverts the priority. At ₹1L/month a 60% basic leaves a healthy +₹3,714 residual and never clamps. At ₹25k/month it clamps at −₹1,621. The absorption factor itself (1.6681 below the cap, 1.5481 above) is confirmed exactly and is now pinned to the decomposition by test.
New finding — the LOP month that deducts nothing D9 was filed as an under-deduction. It is worse than that, and the test that pins it found the sharper version: annualising a loss-of-pay month can zero the deduction outright.

An employee on ₹24,00,000 takes a month at ₹80,000. The old form annualises that to ₹9,60,000, which lands under the new regime's ₹12,00,000 rebate limit — so s.87A wipes the liability out and the month withholds nothing. If it happens in March there is no later month to correct it in, because nothing ever trued up. The employee meets the shortfall at assessment, with interest under s.234B/C, on a salary where TDS was supposed to be complete.

Under the true-up the eleven months already earned still count, the annual estimate stays at ₹22,80,000, and March collects the balance. Both halves are asserted: a_lop_month_does_not_collapse_the_year_and_zero_the_deduction.
What retiring engine C actually cost — three defects deeper than the two methods Swapping the two method bodies for a delegation would have been wrong. Engine C's callers subtract the standard deduction themselves before calling, while PayrollCalculatorService applies it internally -- so a naive delegation double-deducts. Three further defects sit in the callers, not in the two methods this document named:
  • The standard deduction is hardcoded at ₹75,000 for both regimes (:1297). The old regime's is ₹50,000, so every old-regime comparison is already wrong before the slabs are reached.
  • Cess is applied by the caller (:1302, :1309) on top of a slab result, whereas engine A returns a cess-inclusive total. Delegating without removing the caller's cess reproduces the exact bug that got engine D deleted.
  • calculateProfessionalTax() (:1570) is a fabricated PT table that ignores the state entirely -- the same class of defect as the eight invented jurisdictions in D0, on a live endpoint, and not previously identified.
So retiring engine C was a rewrite of the /compare and /what-if handlers, not a body swap. Done: callers now pass annual gross and read taxable_income and total_tax back, so the standard deduction is regime-correct for free and cess is applied once, where it is computed. Declared deductions go to the engine as a section map rather than being summed into a single subtraction — the engine caps 80C at ₹1.5L and 80D on its own limit, which one subtraction cannot, and which is why a what-if with a ₹3L 80C declaration used to under-project.

The vendor argument for doing it at all: Keka's regime comparison and its monthly TDS both read the same IT statement; so do Zoho's Tax Computation and greytHR's Income Tax Statement. Nobody in this market runs a second engine behind the comparison screen, because the employee elects on that screen and s.115BAC makes the election consequential. A simulator that disagrees with payroll is worse than no simulator.
Correction — the overtime divisor is not the defect Both revisions listed basic / 208 among the defects D3 fixes by removal. 208 is correct: it is the statutory 26-day month × 8 hours, the same 26 the Minimum Wages Act uses for a daily rate. The code's own comment gave a wrong reason for a right number ("4-week month"), which is how it would eventually get "corrected" to 240.

The real exposure is the base. Factories Act s.59 pays overtime on the "ordinary rate of wages", defined to include allowances and exclude only bonus and overtime itself. Paying on basic alone understates it by roughly 60% at a 40% basic. Left unchanged deliberately -- whether this organisation pays overtime on basic or on ordinary wages is a pay-policy decision with back-pay consequences, not a defect to silently correct.
